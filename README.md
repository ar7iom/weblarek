# Проектная работа "Веб-ларек"

Стек: HTML, SCSS, TS, Vite

Структура проекта:

- src/ — исходные файлы проекта
- src/components/ — папка с JS компонентами
- src/components/base/ — папка с базовым кодом
- src/components/view/ — компоненты представления

Важные файлы:

- index.html — HTML-файл главной страницы
- src/types/index.ts — файл с типами
- src/main.ts — точка входа приложения
- src/scss/styles.scss — корневой файл стилей
- src/utils/constants.ts — файл с константами
- src/utils/utils.ts — файл с утилитами

## Установка и запуск

Создайте в корне проекта файл `.env`:

```env
VITE_API_ORIGIN=https://larek.ffapi.ru
```

Адрес указывается без завершающего слеша.
После изменения `.env` необходимо перезапустить сервер разработки.

Для установки и запуска проекта необходимо выполнить команды

```
npm install
npm run dev
```

или

```
yarn
yarn dev
```

## Сборка

```
npm run build
```

или

```
yarn build
```

# Интернет-магазин «Web-Larёk»

«Web-Larёk» — это интернет-магазин с товарами для веб-разработчиков, где пользователи могут просматривать товары, добавлять их в корзину и оформлять заказы. Сайт предоставляет удобный интерфейс с модальными окнами для просмотра деталей товаров, управления корзиной и выбора способа оплаты, обеспечивая полный цикл покупки с отправкой заказов на сервер.

## Архитектура приложения

Код приложения разделен на слои согласно парадигме MVP (Model-View-Presenter), которая обеспечивает четкое разделение ответственности между классами слоев Model и View. Каждый слой несет свой смысл и ответственность:

Model — слой данных, отвечает за хранение и изменение данных.
View — слой представления, отвечает за отображение данных на странице.
Presenter — презентер содержит основную логику приложения и отвечает за связь представления и данных.

Взаимодействие между классами обеспечивается использованием событийно-ориентированного подхода. Модели и Представления генерируют события при изменении данных или взаимодействии пользователя с приложением, а Презентер обрабатывает эти события используя методы как Моделей, так и Представлений.

### Базовый код

#### Класс Component

Является базовым классом для всех компонентов интерфейса.
Класс является дженериком и принимает в переменной `T` тип данных, которые могут быть переданы в метод `render` для отображения.

Конструктор:
`constructor(container: HTMLElement)` — принимает ссылку на DOM элемент за отображение, которого он отвечает.

Поля класса:
`container: HTMLElement` — поле для хранения корневого DOM элемента компонента.

Методы класса:
`render(data?: Partial<T>): HTMLElement` — Главный метод класса. Он принимает данные, которые необходимо отобразить в интерфейсе, записывает эти данные в поля класса и возвращает ссылку на DOM-элемент. Предполагается, что в классах, которые будут наследоваться от `Component` будут реализованы сеттеры для полей с данными, которые будут вызываться в момент вызова `render` и записывать данные в необходимые DOM элементы.
`setImage(element: HTMLImageElement, src: string, alt?: string): void` — утилитарный метод для модификации DOM-элементов `<img>`

#### Класс Api

Содержит в себе базовую логику отправки запросов.

Конструктор:
`constructor(baseUrl: string, options: RequestInit = {})` — В конструктор передается базовый адрес сервера и опциональный объект с заголовками запросов.

Поля класса:
`baseUrl: string` — базовый адрес сервера
`options: RequestInit` — объект с заголовками, которые будут использованы для запросов.

Методы:
`get(uri: string): Promise<object>` — выполняет GET запрос на переданный в параметрах ендпоинт и возвращает промис с объектом, которым ответил сервер
`post(uri: string, data: object, method: ApiPostMethods = 'POST'): Promise<object>` — принимает объект с данными, которые будут переданы в JSON в теле запроса, и отправляет эти данные на ендпоинт переданный как параметр при вызове метода. По умолчанию выполняется `POST` запрос, но метод запроса может быть переопределен заданием третьего параметра при вызове.
`handleResponse(response: Response): Promise<object>` — защищенный метод проверяющий ответ сервера на корректность и возвращающий объект с данными полученный от сервера или отклоненный промис, в случае некорректных данных.

#### Класс EventEmitter

Брокер событий реализует паттерн "Наблюдатель", позволяющий отправлять события и подписываться на события, происходящие в системе. Класс используется для связи слоя данных и представления.

Конструктор класса не принимает параметров.

Поля класса:
`_events: Map<string | RegExp, Set<Function>>)` — хранит коллекцию подписок на события. Ключи коллекции — названия событий или регулярное выражение, значения — коллекция функций обработчиков, которые будут вызваны при срабатывании события.

Методы класса:
`on<T extends object>(event: EventName, callback: (data: T) => void): void` — подписка на событие, принимает название события и функцию обработчик.
`emit<T extends object>(event: string, data?: T): void` — инициализация события. При вызове события в метод передается название события и объект с данными, который будет использован как аргумент для вызова обработчика.
`trigger<T extends object>(event: string, context?: Partial<T>): (data: T) => void` — возвращает функцию, при вызове которой инициализируется требуемое в параметрах событие с передачей в него данных из второго параметра.

## Данные

### Сущности

В приложении используются две сущности, которые описывают данные, — товар и покупатель. Их можно описать такими интерфейсами:

#### Товар:

```
export interface IProduct {
  id: string;
  description: string;
  image: string;
  title: string;
  category: string;
  price: number | null;
}
```

Где:

- id — уникальный идентификатор товара;
- description — описание товара;
- image — строковый путь к изображению товара, полученный с сервера;
- title — наименование товара;
- category — категория товара;
- price — цена товара, где значение null означает,что цена не указана и товар недоступен для покупки.

#### Покупатель:

```
export interface IBuyer {
  payment: TPayment;
  email: string;
  phone: string;
  address: string;
}
```

Где:

- payment — способ оплаты (см. ["Дополнительные типы"](#дополнительные-типы));
- email — адрес эелектронной почты покупателя;
- phone — контактный телефон покупателя;
- address — адрес доставки, указанный покупателем.

### Дополнительные типы

```ts
export type TPayment = 'card' | 'cash' | '';

export type BuyerErrors = Partial<Record<keyof IBuyer, string>>;
```

`TPayment` описывает способ оплаты:

- `card` — оплата картой;
- `cash` — оплата наличными;
- пустая строка — способ оплаты ещё не выбран.

`BuyerErrors` описывает ошибки проверки данных покупателя. Ключи соответствуют полям IBuyer, значения содержат сообщения об ошибках. Поля необязательные. Если ошибок нет, возвращается пустой объект.

## Модели данных

Для учёта данных в приложении используется три класса, которые разделены между собой по смыслу и зонам ответственности:

- хранение товаров, которые можно купить в приложении;
- хранение товаров, которые пользователь выбрал для покупки;
- данные покупателя, которые тот должен указать при оформлении заказа.

### Класс Products

Расположен в файле `src/components/Products.ts`.

Отвечает за хранение списка товаров каталога и товара, выбранного для подробного просмотра. Позволяет заменить список товаров, получить его, найти товар по идентификатору, а также сохранить и получить выбранный товар.

Класс не выполняет запросы к серверу и не работает с HTML-разметкой. Данные передаются в модель через её методы.

#### Создание экземпляра

`constructor(events: IEvents)`

Принимает общий брокер событий приложения: `new Products(events)`.

При создании экземпляра список товаров пуст, выбранный товар отсутствует.

#### Поля

- `protected events: IEvents` — общий брокер событий приложения.

- `protected items: IProduct[] = []` — массив товаров каталога. Начальное значение — пустой массив.
- `protected preview: IProduct | null = null` — товар, выбранный для подробного просмотра. Начальное значение — `null`.

Поля недоступны для прямого обращения из внешнего TypeScript-кода. Для работы с данными используются публичные методы класса.

#### Методы

- `setItems(items: IProduct[]): void` — заменяет список товаров переданным массивом. Параметр items содержит новый список товаров. Метод сохраняет ссылку на массив, не создавая копию. Не изменяет выбранный товар и не возвращает значения.

- `getItems(): IProduct[]` — возвращает сохранённый массив товаров без копирования. Не принимает параметров. Если список ещё не задан, возвращает пустой массив.

- `getProduct(id: string): IProduct | undefined` — находит первый товар с указанным идентификатором. Принимает id — строковый идентификатор товара. Возвращает найденный товар либо undefined, если товар отсутствует в каталоге.

- `setPreview(product: IProduct | null): void` — сохраняет товар для подробного просмотра. Принимает объект товара либо null для сброса выбора. Не изменяет список товаров и не возвращает значения.

- `getPreview(): IProduct | null` — возвращает выбранный товар либо null, если товар не выбран. Не принимает параметров.

#### События

- `products:update` — уведомляет об обновлении каталога товаров. Генерируется в `setItems()` после сохранения массива товаров. Актуальный каталог доступен через `getItems()`.

Данные в событии не передаются. Презентер получает актуальное состояние через методы модели и обновляет соответствующие представления.

### Класс Cart

Расположен в файле `src/components/Cart.ts`.

Отвечает за хранение товаров, выбранных для покупки. Позволяет добавлять и удалять товары, очищать корзину, получать список товаров, их количество и общую стоимость, а также проверять наличие товара по идентификатору.

Не работает с HTML-разметкой и не выполняет запросы к серверу.

#### Создание экземпляра

`constructor(events: IEvents)`

Принимает общий брокер событий приложения: `new Cart(events)`.
При создании корзина пуста.

#### Поля

- `protected events: IEvents` — общий брокер событий приложения.

- `protected items: IProduct[] = []` — массив товаров корзины. Начальное значение — пустой массив.

#### Методы

- `getItems(): IProduct[]` — возвращает массив товаров корзины без копирования. Не принимает параметров.

- `addItem(product: IProduct): void` — добавляет переданный товар в корзину. Не добавляет товар, если его цена равна null или товар с таким id уже есть в корзине. Не возвращает значения.

- `removeItem(product: IProduct): void` — удаляет товар по идентификатору переданного объекта. Если товара нет, состав корзины не изменяется. Не возвращает значения.

- `clear(): void` — очищает корзину. Не принимает параметров и не возвращает значения.

- `getTotal(): number` — возвращает сумму цен товаров. При расчёте цена null учитывается как 0. Для пустой корзины возвращает 0. Не принимает параметров.

- `getCount(): number` — возвращает количество товаров. Для пустой корзины возвращает 0. Не принимает параметров.

- `hasItem(id: string): boolean` — проверяет наличие товара по строковому идентификатору. Возвращает true, если товар найден, иначе false.

#### События

- `cart:update` — уведомляет об изменении содержимого корзины. Генерируется после успешного добавления товара в `addItem()`, удаления существующего товара в `removeItem()` и очистки непустой корзины в `clear()`.

Данные в событии не передаются. Презентер получает актуальный список товаров через `getItems()`, общую стоимость через `getTotal()`, а количество товаров через `getCount()`.

Событие позволяет обновить представление корзины и счётчик товаров в шапке страницы.

### Класс Buyer

Расположен в файле `src/components/Buyer.ts`.

Отвечает за хранение данных покупателя: способа оплаты, адреса, email и телефона. Позволяет сохранять данные по частям, получать их, очищать и проверять заполненность.

Не работает с HTML-разметкой и не отправляет данные на сервер.

#### Создание экземпляра

`constructor(events: IEvents)`

Принимает общий брокер событий приложения: `new Buyer(events)`.
Изначально все поля содержат пустые строки.

#### Поля

- `protected events: IEvents` — общий брокер событий приложения.

- `protected payment: TPayment = ''` — способ оплаты. Пустая строка означает, что способ оплаты не выбран.

- `protected address: string = ''` — адрес покупателя.

- `protected email: string = ''` — электронная почта покупателя.

- `protected phone: string = ''` — телефон покупателя.

#### Методы

- `setData(data: Partial<IBuyer>): void` — сохраняет переданные поля покупателя. Поля, которые не переданы или имеют значение undefined, остаются без изменений. Пустая строка сохраняется. Не возвращает значения.

- `getData(): IBuyer` — возвращает новый объект со всеми данными покупателя. Не принимает параметров.

- `clear(): void` — сбрасывает все поля в пустые строки. Не принимает параметров и не возвращает значения.

- `validate(): BuyerErrors` — проверяет заполненность данных. Для способа оплаты проверяет отсутствие выбора, а для адреса, email и телефона — пустую строку после `trim()`. Возвращает объект с сообщениями об ошибках по полям. Если ошибок нет, возвращает пустой объект. Не принимает параметров и не изменяет данные. Формат email и телефона не проверяет.

#### События

- `buyer:update` — уведомляет об обновлении данных покупателя. Генерируется после сохранения данных в `setData()` и сброса в `clear()`. Данные в событии не передаются: актуальное состояние доступно через `getData()`, ошибки валидации — через `validate()`.

## Слой коммуникации

Слой коммуникации отвечает за получение товаров с сервера и отправку заказа. Он не управляет разметкой и не изменяет модели данных напрямую.

### Класс ApiMethods

Расположен в файле `src/components/ApiMethods.ts`.

Предоставляет методы для получения каталога товаров и отправки заказа на сервер.

Использует базовый клиент Api через композицию: готовый API-клиент передаётся в конструктор и сохраняется в поле класса. ApiMethods не наследуется от Api.

#### Конструктор

`constructor(api: IApi)`

Принимает api — объект, реализующий интерфейс IApi.
Этот объект используется для выполнения GET- и POST-запросов.

#### Поля

- `protected api: IApi` — API-клиент для выполнения запросов.

#### Методы

- `getProducts(): Promise<IProductsResponse>` — выполняет GET-запрос на /product/. Не принимает параметров. Возвращает Promise с объектом ответа сервера: total — количество товаров, items — массив товаров.

- `createOrder(order: IOrder): Promise<IOrderResult>` — выполняет POST-запрос на /order/. Принимает order — данные покупателя, общую сумму и массив идентификаторов товаров. Возвращает Promise с подтверждением заказа: id — идентификатор заказа, total — сумма заказа.

Ошибки запросов передаются вызывающему коду через отклонённый Promise. Обработка ошибок выполняется в main.ts.

### Типы данных коммуникационного слоя

- `IProductsResponse` — ответ сервера при получении каталога. Содержит `total: number` и `items: IProduct[]`.

- `IOrder` — данные для отправки заказа. Использует поля IBuyer, но исключает пустую строку из допустимых способов оплаты. Дополнительно содержит `total: number` и `items: string[]`. В items передаются идентификаторы товаров, а не объекты товаров.

- `IOrderResult` — подтверждение заказа от сервера. Содержит `id: string` и `total: number`.

## Слой представления (View)

Слой представления отвечает за отображение данных и взаимодействие пользователя с интерфейсом. Каждый класс управляет своим блоком разметки.

Компоненты представления не обращаются напрямую к моделям данных и API. Они получают подготовленные данные от Презентера, обновляют DOM и генерируют события в ответ на действия пользователя.

Презентер обрабатывает события, вызывает методы моделей и передаёт представлениям обновлённые данные.

### Наследование и композиция

Все компоненты представления наследуются от базового класса `Component<T>`, напрямую или через общие родительские классы.

```text
Component<T>
├── Header
├── Gallery
├── Card<T>
│   ├── CardCatalog
│   ├── CardPreview
│   └── CardBasket
├── Basket
├── Modal
├── Form<T>
│   ├── OrderForm
│   └── ContactsForm
└── Success
```

В `Card` вынесена работа с названием и ценой, общая для всех трёх карточек.

В `Form` вынесена работа с кнопкой отправки, сообщениями об ошибках и обработкой событий формы.

`Modal` не имеет дочерних классов. Подробная карточка, корзина, формы и подтверждение заказа являются самостоятельными компонентами. Их корневые DOM-элементы передаются в модальное окно как содержимое. Эти компоненты также могут отображаться в других контейнерах страницы.

Галерея содержит DOM-элементы карточек каталога, а корзина — DOM-элементы карточек выбранных товаров. Размещение одного компонента внутри другого не является наследованием.

### Типы данных представления

Типы описывают данные, которые Презентер передаёт компонентам для отображения. Типы карточек создаются на основе `IProduct` с помощью `Pick`, а типы форм используют поля `IBuyer`. Дополнительные поля описывают состояние интерфейса.

#### Данные шапки

```ts
export interface HeaderData {
  counter: number;
}
```

где:

- `counter` — количество товаров в корзине, отображаемое на кнопке в шапке.

#### Данные галереи

```ts
export interface GalleryData {
  catalog: HTMLElement[];
}
```

где:

- `catalog` — массив готовых DOM-элементов карточек товаров для размещения в галерее.

#### Данные базовой карточки

```ts
export type CardData = Pick<IProduct, 'title' | 'price'>;
```

Тип содержит общие данные для всех видов карточек:

- `title: string` — название товара;
- `price: number | null` — цена товара в синапсах. Значение `null` означает, что товар недоступен для покупки.

#### Данные карточки каталога

```ts
export type CardCatalogData = CardData & Pick<IProduct, 'image' | 'category'>;
```

Тип включает поля `CardData` и дополнительно содержит:

- `image: string` — адрес изображения товара;
- `category: string` — категория товара, определяющая текст и оформление метки.

#### Данные подробной карточки

```ts
export type CardPreviewData = CardData &
  Pick<IProduct, 'image' | 'category' | 'description'> & {
    buttonText: string;
    buttonDisabled: boolean;
  };
```

Тип включает поля `CardData` и дополнительно содержит:

- `image: string` — адрес изображения товара;
- `category: string` — категория товара;
- `description: string` — подробное описание товара;
- `buttonText: string` — текст кнопки действия;
- `buttonDisabled: boolean` — состояние блокировки кнопки: `true` — заблокирована, `false` — доступна.

Текст и доступность кнопки подготавливает Презентер на основе цены товара и его наличия в корзине.

#### Данные карточки корзины

```ts
export type CardBasketData = CardData & {
  index: number;
};
```

Тип включает поля `CardData` и дополнительно содержит:

- `index: number` — порядковый номер товара в корзине, начиная с 1. Не является идентификатором товара.

#### Данные корзины

```ts
export interface BasketData {
  list: HTMLElement[];
  total: number;
  buttonDisabled: boolean;
}
```

где:

- `list` — массив готовых DOM-элементов карточек товаров корзины;
- `total` — общая стоимость товаров в синапсах, полученная из модели корзины через Презентер.
- `buttonDisabled` — `true` блокирует кнопку, `false` делает доступной.

#### Данные модального окна

```ts
export interface ModalData {
  content: HTMLElement;
}
```

где:

- `content` — корневой DOM-элемент самостоятельного компонента, который нужно отобразить внутри модального окна.

#### Общие данные форм

```ts
export interface FormData {
  valid: boolean;
  errors: string;
}
```

где:

- `valid` — доступность отправки формы: `true` — отправка разрешена, `false` — кнопка отправки заблокирована;
- `errors` — текст ошибок для отображения в форме. Пустая строка очищает сообщение.

Оба значения подготавливает Презентер на основе результата проверки данных модели.

#### Данные формы оплаты и доставки

```ts
export type OrderFormData = FormData & Pick<IBuyer, 'payment' | 'address'>;
```

Тип включает поля `FormData` и дополнительно содержит:

- `payment: TPayment` — выбранный способ оплаты: `'card'` — онлайн, `'cash'` — при получении, `''` — способ ещё не выбран;
- `address: string` — адрес доставки.

Поля `valid` и `errors` отражают состояние только первого шага оформления: выбора оплаты и заполнения адреса.

#### Данные формы контактов

```ts
export type ContactsFormData = FormData & Pick<IBuyer, 'email' | 'phone'>;
```

Тип включает поля `FormData` и дополнительно содержит:

- `email: string` — электронная почта покупателя;
- `phone: string` — телефон покупателя.

Поля `valid` и `errors` отражают состояние второго шага оформления: заполнения контактных данных.

#### Данные подтверждения заказа

```ts
export type SuccessData = Pick<IOrderResult, 'total'>;
```

где:

- `total: number` — сумма списанных синапсов из успешного ответа сервера, отображаемая в подтверждении заказа.

Базовый метод `render(data?: Partial<T>): HTMLElement` позволяет обновлять данные компонента частично. Переданные свойства применяются через сеттеры, после чего метод возвращает корневой DOM-элемент.

### Передача событий

Для передачи событий используется существующий интерфейс `IEvents`.

Компоненты с пользовательскими действиями получают брокер событий через конструктор. У карточек обработчик действия может передаваться отдельно:

```ts
export interface CardActions {
  onClick: () => void;
}
```

Презентер создаёт обработчик и связывает его с конкретным товаром. Обработчик генерирует событие через брокер событий.

Такой подход позволяет передавать идентификатор товара в событии, не добавляя его в типы отображаемых данных карточки.

### Класс CardCatalog

Отвечает за карточку товара в каталоге. Использует шаблон `#card-catalog`.

Поля названия и цены наследуются от `Card`.

### Класс Modal

Наследуется от `Component<ModalData>`. Отвечает за показ и скрытие модального окна и размещение переданного содержимого. Использует корневой элемент `#modal-container` с классом `.modal`.

#### Создание экземпляра

`constructor(container: HTMLElement)`

Принимает корневой элемент модального окна. Брокер событий не требуется: кнопка закрытия и фон вызывают собственный метод `close()`.

#### Поля

- `protected closeButton: HTMLButtonElement` — кнопка `.modal__close`.
- `protected contentElement: HTMLElement` — область сменяемого содержимого `.modal__content`.
- `protected modalContainer: HTMLElement` — внутренняя область `.modal__container`. Клик внутри неё не всплывает до фона.
- `protected readonly container: HTMLElement` — корневой элемент, унаследованный от `Component`.

Элементы находятся один раз в конструкторе и сохраняются в полях. Все обработчики устанавливаются один раз в конструкторе.

#### Сеттеры

- `set content(value: HTMLElement)` — заменяет дочерние элементы `.modal__content` переданным элементом через `replaceChildren()`.

#### Методы

- `open(): void` — добавляет `modal_active` корневому элементу.
- `close(): void` — удаляет `modal_active` с корневого элемента.
- `render(data?: Partial<ModalData>): HTMLElement` — унаследованный метод, устанавливает содержимое и возвращает корневой элемент; без аргументов возвращает существующую разметку.

Для показа Презентер передаёт разметку нужного компонента в `content`, затем вызывает `open()`. Модальное окно не знает о моделях, товарах и этапах оформления. Нажатие крестика или фона закрывает окно; клики внутри `.modal__container` останавливаются через `stopPropagation()`. Сам компонент событий не генерирует.

### Класс Form<T extends FormData>

Абстрактный класс, наследуется от `Component<T>`.

Содержит общий функционал форм оформления заказа: управление кнопкой отправки, отображение ошибок и обработку ввода и отправки формы.

#### Создание экземпляра

`protected constructor(container: HTMLFormElement, events: IEvents)`

Принимает корневой элемент формы и брокер событий.

#### Поля

- `protected submitButton: HTMLButtonElement` — кнопка `button[type="submit"]`.
- `protected errorsElement: HTMLElement` — область ошибок `.form__errors`.
- `protected events: IEvents` — брокер событий.

#### Сеттеры

- `set valid(value: boolean)` — разблокирует кнопку отправки при `true` и блокирует при `false`.
- `set errors(value: string)` — отображает сообщение об ошибке или очищает его при передаче пустой строки.

#### Методы

- `protected onInputChange(field: keyof IBuyer, value: string): void` — генерирует событие изменения поля.
- `protected abstract onSubmit(): void` — абстрактный метод; наследник отправляет событие своего шага. Базовый обработчик отменяет стандартную отправку и не вызывает метод, если кнопка отключена.

Обработчик `input` определяет изменённое поле и передаёт его имя и значение в `onInputChange`.

Обработчик `submit` отменяет стандартную отправку формы и вызывает `onSubmit`, если кнопка отправки доступна.

Компонент не проверяет данные самостоятельно. Презентер обновляет модель `Buyer`, получает результат `validate()` и передаёт форме значения `valid` и `errors`.

Презентер определяет доступность каждого шага только по относящимся к нему полям. Незаполненные контакты не должны блокировать первый шаг.

#### События

- `buyer:change` — изменение данных покупателя. Передаёт имя поля и его новое значение.

Для поля `payment` передаётся значение существующего типа `TPayment`.

Обработчик `submit` сначала вызывает `event.preventDefault()`, затем проверяет `submitButton.disabled`. При отключённой кнопке отправка не выполняется.

- `contacts:submit` — при нажатии на доступную кнопку «Оплатить».

Кнопка «Оплатить» доступна только при заполненных полях и отсутствии ошибок второго шага.

Отправку заказа на сервер выполняет Презентер через коммуникационный слой. Представление не вызывает API и не очищает модели самостоятельно.

### Класс Success

Наследуется от `Component<SuccessData>`.

Отвечает за сообщение об успешном оформлении заказа и отображение списанной суммы. Использует шаблон `#success`.

#### Создание экземпляра

`constructor(container: HTMLElement, events: IEvents)`

Принимает корневой элемент клонированного шаблона и брокер событий.

#### Поля

- `protected descriptionElement: HTMLElement` — сообщение о списанной сумме `.order-success__description`.
- `protected closeButton: HTMLButtonElement` — кнопка `.order-success__close`.
- `protected events: IEvents` — брокер событий.

#### Сеттеры

- `set total(value: number)` — отображает текст «Списано N синапсов», где N — сумма из ответа сервера.

#### События

- `success:close` — нажатие кнопки «За новыми покупками!».

Презентер обрабатывает событие и закрывает модальное окно.

Компонент отображается только после успешного ответа сервера. Очистку корзины и данных покупателя выполняет Презентер, после чего обновляет связанные представления.

### События слоя представления

Названия ниже описывают пользовательские действия и запросы к Презентеру. Они не означают, что представление самостоятельно изменяет модели.

| Событие           | Источник                    | Данные                   | Действие Презентера                         |
| ----------------- | --------------------------- | ------------------------ | ------------------------------------------- |
| `basket:open`     | `Header`                    | Без данных               | Отобразить корзину                          |
| `product:open`    | Обработчик `CardCatalog`    | `IProduct`               | Выбрать товар и показать подробную карточку |
| `product:toggle`  | Обработчик `CardPreview`    | `{ id: IProduct['id'] }` | Добавить или удалить товар                  |
| `product:remove`  | Обработчик `CardBasket`     | `{ id: IProduct['id'] }` | Удалить товар и обновить корзину            |
| `order:open`      | `Basket`                    | Без данных               | Показать первый шаг оформления              |
| `buyer:change`    | `OrderForm`, `ContactsForm` | Имя поля и его значение  | Изменить данные покупателя и состояние форм |
| `order:submit`    | `OrderForm`                 | Без данных               | Показать второй шаг оформления              |
| `contacts:submit` | `ContactsForm`              | Без данных               | Проверить данные и отправить заказ          |
| `success:close`   | `Success`                   | Без данных               | Закрыть подтверждение заказа                |

При неуспешной отправке заказа Презентер сохраняет товары и данные покупателя, отображает ошибку через `errors` формы и возвращает возможность повторной отправки.

## Презентер

Презентер реализован в `src/main.ts` без отдельного класса: приложение содержит одну страницу. Он связывает модели, представления и API, регистрирует обработчики событий и координирует сценарии пользователя. Компоненты представления не обращаются к моделям или API напрямую.

### Инициализация

Создаётся один общий `EventEmitter`, передаваемый моделям и компонентам, которым нужен брокер. `ApiMethods` получает экземпляр `Api` через композицию. Представления создаются на основе существующих контейнеров или клонов HTML-шаблонов. `Modal` получает только контейнер. Начальное значение счётчика берётся через `cartModel.getCount()`. Подписки регистрируются до запроса каталога.

### Состояние запроса

- `isOrderSubmitting: boolean = false` — признак незавершённого запроса оформления. Не содержит данные заказа и не дублирует модель покупателя. Устанавливается перед запросом, сбрасывается в `finally`. Повторная отправка при `true` игнорируется.

### Вспомогательные функции

- `updateBasket(): void` — получает товары из `Cart`, создаёт элементы через `CardBasket`, передаёт их вместе с суммой и состоянием кнопки в `Basket.render()`. Не открывает окно и не меняет модель.
- `getFormState(errors: BuyerErrors, fields: (keyof IBuyer)[]): { valid: boolean; errors: string }` — собирает сообщения только для полей текущего шага и возвращает его валидность.
- `updateOrderForm(): void` — передаёт в первую форму оплату, адрес, ошибки этих полей и состояние кнопки.
- `updateContactsForm(): void` — передаёт контакты и ошибки второго шага. Кнопка доступна только при валидных контактах и `isOrderSubmitting === false`.

### Каталог и превью

После `apiMethods.getProducts()` массив `response.items` сохраняется через `productsModel.setItems()`. Обработчик `products:update` создаёт `CardCatalog` для каждого товара и передаёт готовые элементы в `Gallery.render()`.

Обработчик `product:open` получает `IProduct`, сохраняет его через `setPreview()`, проверяет корзину и подготавливает данные `CardPreview`. Отображение выполняется в обработчике запроса открытия модального окна. Товар без цены (`null`) или с ценой `0` недоступен для покупки по бизнес-правилу приложения; кнопка имеет текст «Недоступно». Для остальных товаров отображается «Купить» или «Удалить из корзины».

`product:toggle` передаёт `{ id: IProduct['id'] }`. Презентер получает выбранный товар, проверяет идентификатор и доступность, затем вызывает `addItem()` либо `removeItem()` модели корзины. После операции превью закрывается. При повторном открытии текст кнопки рассчитывается заново.

### Корзина

`basket:open` вызывает `updateBasket()`, помещает разметку корзины в `Modal` и открывает окно. `product:remove` ищет товар по идентификатору в корзине и вызывает `removeItem()`; окно остаётся открытым. Обработчик `cart:update` обновляет строки, нумерацию, сумму, доступность оформления и счётчик шапки. Это уведомление отправляет модель, повторный `emit` после вызова её метода не требуется.

Если корзина пуста, представление `Basket` показывает «Корзина пуста», а Презентер отключает кнопку оформления. Дополнительная проверка перед отправкой заказа запрещает отправку пустой корзины на сервер.

### Оформление заказа

`order:open` показывает форму оплаты и адреса с актуальными данными модели. `order:submit` показывает контактную форму. `buyer:change` передаёт `{ field: keyof IBuyer; value: string }`; Презентер проверяет допустимые значения оплаты и вызывает `buyerModel.setData()`. Обработчик `buyer:update` обновляет обе формы без переключения содержимого модалки.

`contacts:submit` проверяет отсутствие текущего запроса, результаты `validate()` по обоим шагам, выбранную оплату и непустую корзину. Формируется `IOrder`: данные покупателя, массив идентификаторов и сумма из модели. Перед запросом устанавливается `isOrderSubmitting`, кнопка блокируется. Редактирование контактов не разблокирует её до завершения запроса.

После успешного `apiMethods.createOrder(order)` модели корзины и покупателя очищаются; `Success` получает `total` из ответа сервера и показывает списанную сумму. При ошибке данные не очищаются, показывается сообщение о неудаче. В `finally` флаг запроса сбрасывается и состояние контактной формы пересчитывается. Событие `success:close` закрывает модальное окно.

### Источники событий

Модели отправляют `products:update`, `cart:update` и `buyer:update` после сохранения данных. Формы и шапка используют переданный брокер. Карточки получают `CardActions`: callback выполняется при клике и отправляет пользовательское событие. Его объявление в `main.ts` не означает отправку события при создании карточки. Презентер обрабатывает действия, вызывает модели и передаёт подготовленные данные представлениям; не подменяет уведомления модели ручным `emit`.
